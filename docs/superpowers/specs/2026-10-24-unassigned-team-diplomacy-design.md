# 原队伍为 -1 的玩家：可还原的外交模板

日期：2026-10-24。状态：用户批准并选择内联实施；R19.3-Test 已实现并通过离线验证，实际游戏验收待进行。原方案与取舍保留如下。

## 目标与原因

让原生队伍为 `-1` 的普通玩家，也能通过现有“把选中玩家加入队伍”和“恢复原队伍”入口，临时使用目标队伍的联盟关系，之后恢复第一次操作前的关系。当前游戏的 `SetPlayerTeam` 拒绝把新队伍设为 `-1`，因此这类玩家从始至终保留原生队伍 `-1`，不进行真实换队。

## 方案取舍

1. 真实加入普通队伍后再调用 `SetPlayerTeam(-1)`：原生参数校验拒绝恢复，已排除。
2. 强写队伍字段或修改游戏函数绕过校验：不能保证队伍成员表一致性，且超出本次最小改动范围，已排除。
3. 保留 `-1`，临时套用外交模板、恢复原始双向联盟关系：用户已确认采用。代价是地图使用 `GetPlayerTeam` 判断时仍会读到 `-1`；不能宣称真正改变了原生队伍编号。

## 确定的行为

- 使用现有队伍下拉列表和快捷键入口，不增加新的操作入口。目标仍为队伍 1～12、中立敌对、中立被动及恢复原队伍。
- 只为原队伍 `-1` 的普通玩家增加分支；非负原队伍和现有中立槽位的行为保持不变。
- 复用现有模板选择规则：普通队伍使用该队伍的合适参考玩家；没有参考玩家时沿用既有关系生成规则；中立目标使用现有对应中立模板。不自行猜测或改写原生队伍值。
- 只处理既有六类联盟关系（类型 0～5），不调用控制权功能、不改变单位归属，也不额外修改共享控制权相关类型。
- 第一次成功操作保存原始 `-1` 和涉及玩家的双向联盟关系。之后切换多少次目标，也不以中间状态覆盖真正原始状态；继续沿用既有快照合并规则，新增涉及玩家的关系在首次涉及时记录。
- 恢复只还原保存的联盟关系，确认目标玩家原生队伍仍为 `-1`，不调用 `SetPlayerTeam`，更不把 `-1` 替换成队伍 1 或中立编号。

## 监视与安全约束

- 监视仍为只读，不因读取而建立、覆盖或删除恢复快照。
- 为新分支提供可核对的联盟回读；只有玩家身份和当前双向关系与最近一次模板匹配，才显示“队伍 N（外交模板）；原生队伍编号 -1”。中立模板沿用对应名称。
- 没有已验证模板时继续显示“未分配普通队伍（原始值 -1）”；地图改变了关系时，明确提示关系变化，不展示过期的成功状态。
- 玩家身份、快照所属进程或玩家、原生队伍不符时，在写入前拒绝；异常状态不得用新快照覆盖第一次快照。旧进程快照不得用于新进程。
- 写入前完成参数、快照和资源检查；逐项回读验证。操作失败则尝试退回本次操作前的关系，并报告回滚是否成功；恢复失败保留原快照，不伪报成功。
- 联盟快照中若出现其他 `-1` 玩家，必须明确编码、解码该值，不能截断成队伍 63。若响应协议需要扩展，则同步升级 Python 与 DLL 协议，并拒绝混用旧 helper。
- 旧监视操作、名字读取、普通玩家换队、复制及其他扩展不作顺带重构；不改现有 native 指纹、ABI 或读取模式。
