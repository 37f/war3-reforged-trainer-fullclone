# R22：当前地图任务及实际完成／失败条件

日期：2026-10-25。状态：用户已选择自动识别当前地图并分析脚本，并确认“按设计实施”；独立可实施性检查未发现需要补问的关键问题。

## 目标和用户已作出的选择

进入自定义战役章节或独立地图后，在修改器中先检索，再显示该地图的任务及实际完成、失败条件。用户明确需要地图脚本中的实际判定，包括隐藏条件、计数要求及直接失败触发，不能只抄任务面板说明。

用户已选择：**自动识别当前地图并分析脚本，无法解析时明确提示**。不要求手选战役或章节，不修改游戏任务、触发器、存档、地图或战役。R21 和此前全部扩展继续保留。

“所有”是检索当前章节可取得脚本中的任务定义、任务条目、完成／失败状态写入点及关卡胜败调用，并报告关联和覆盖缺口。它不是对任意加密、混淆、动态程序都保证恢复出完整规则。尚未运行的任务创建代码也要检索，但只能标为“脚本任务定义”，不能宣称任务已在本次游戏创建、显示或完成。

## 方案比较

1. **用户已选：自动定位当前地图资源，再只读分析脚本。** 延续 R21 无需选文件的体验，能够追踪面板外的直接失败判定。新增难点是准确定位当前脚本来源；这必须先验证，不能靠地图名称、对象数或相似内容推测章节。
2. **未选：用户手动选择战役／地图和章节后分析。** 可以复用 R20 的只读 MPQ 读取，定位更直接，但每次要自己选择文件，无法直接满足本次体验。不作为自动识别失败时的隐式替代。
3. **不采用：仅枚举运行时 quest 状态。** 当前已知 native 能查询完成、失败等标志，却不能说明触发这些变化的事件和条件，也会漏掉未创建任务和直接判负。运行时进度、当前计数、任务是否已触发等实时监视不属于首版范围。

沿用 Python/Tk、现有 StormLib、持久 helper、独立分析模块和本地确定性解析是实现者建议。没有向外部 AI 服务发送脚本的步骤。

## 已完成的只读调查

基线为 R21 提交 `48a3158442094e5c1ed4b654b61e10eb8a3f68f7`；支持的游戏构建仍为已验证的 2.0.4.23745 x64。此前配套 helper 协议为 78。

现有 `source/war3_campaign_catalog.py` 封装了只读 StormArchive、嵌套章节临时副本及字符串表解析。R21 提供游戏连接身份、活跃地图检查、地图会话 token 和队列过期保护，但**没有证明可以定位当前地图脚本或源档案**，不能把现有对象目录冒充脚本读取能力。

只读检查 `亡灵骑士.w3n / necroknight3.w3x`：`war3map.j` 为 147921 字节、3445 行，包含 3 个 CreateQuestBJ 调用、2 个任务完成设置、2 处 CustomDefeatBJ 和 1 处 CustomVictoryBJ，没有 QuestSetFailed 调用。源档案读取前后 SHA-256 与修改时间一致；没有运行地图脚本。

已人工核对的静态样例：

- 第 2616–2621 行：完成检查为 `udg_recruits_CompletedReqs == 3`。其前方三个辅助条件检查 `udg_Quest_ABC_Reqs[1..3]` 的完成状态，动作中分别累计计数。应显示三个条目及最终计数判断，不能只显示变量名就称为已解释全部来源。
- 第 2768–2791 行：“藏身处”任务完成与进入 `gg_rct_Region_018` 有关，并检查 `IsUnitEnemy(GetTriggerUnit(), Player(1)) == true`。需要保留事件与布尔条件的组合，不能简化成任意单位进入即完成。
- 第 1756–1773 行：任何单位死亡事件触发后，检查 `udg_hero1` 是否死亡；动作等待 2 秒后调用 CustomDefeatBJ。第 1785–1788 行另有指定 `gg_unit_U600_0169` 死亡后直接判负的注册。它们属于关卡直接失败条件，不能伪造为某个任务的失败状态。
- 第 2270–2279 行的直接胜利动作由其他触发器调用，没有独立注册事件。必须继续追踪调用者，不能显示为无条件胜利。

以上是源脚本证据，不是运行时测试或新功能验收；第一次调查时未发现运行中的 Warcraft III 进程。

## 阶段一：自动来源定位的可行性门槛

先做限定构建的只读调查，验证从活跃地图上下文确定当前脚本及相关字符串表的路径或资源归属。可以调查两条读取路径：已有地图资源管理器／加载上下文中的原始脚本数据，或由同一上下文确认归属的档案和内部章节路径。具体布局、代码特征和读取方式须由证据决定，本文不预填未知地址。

来源证明至少包含：游戏连接身份、当前地图会话标识、已验证的当前地图资源归属、脚本语言和路径、脚本内容哈希，以及随脚本取得的字符串表来源／哈希。读取开始和结束均检查会话。

禁止用以下方式宣称定位成功：只匹配显示名称、对象 ID 数量、仅比较相似文本、随意选择 Campaigns 目录中第一个同名文件、拿另一个已修改档案替代当前加载数据、把上一章缓存当作本章。若只能取得磁盘候选而无法证明属于当前加载章节，报告“当前脚本来源无法确认”，不发布任务条件。

禁止把目标游戏自己的档案句柄传给本程序打包的另一份 StormLib；如使用文件路径，只在本程序以只读方式重新打开已验证归属的文件。对可能已被修改的源档案，必须核对与当前会话的对应证据；无法排除不一致则拒绝。地图／战役字符串表不能跨章节套用。

新运行时查询仅在确有必要时接入现有持久 helper；使用未占用的只读操作和配套协议升级，不改旧操作含义、native 名称、签名或 hash。查询沿用已有互斥与长生命周期 hook 所有者；排队后重查连接、关闭状态及 hook 归属，不能由旧任务重新注入。

调查可以读现有文件或目标进程，测试时由用户自行进入地图；不安装工具、不调用未知游戏函数、不执行地图脚本、不修改触发器或关闭游戏。开发调查的临时扫描不得变成每次检索的产品流程。

**放行标准：** 在用户控制的至少两个不同章节／地图中确认正确脚本与字符串来源，并验证菜单／换图不会继续发布旧脚本。未达到时继续调查或报告受阻；不得发布一个只会猜测文件的 R22 成品。

## 阶段二：可核对的 JASS 静态分析

首版支持 JASS；Lua、加密／不可读脚本、动态生成且无法取回的代码明确报告不支持或覆盖不完整。这是实现者提出的首版范围，供用户在确认本文时调整。不得因 Lua 中没有匹配 JASS 关键字而显示“0 个任务、完整分析”。

先进行分词、语法解析并记录源位置，再建立函数／触发器／任务对象关联；正则只能用于入口识别或展示，不能靠截取函数附近几行推断实际布尔逻辑。保留大小写、字符串、注释边界、括号、not/and/or 优先级、早返回与 true/false 分支。分析不执行 JASS/Lua。

必须区分：

- 任务创建和名称／说明／必需／发现等设置，任务条目创建与描述；BJ 包装及明确的全局变量、数组和局部别名传递。
- 任务／条目的设置为完成、设置为失败，以及重置为未完成／未失败。不能把 `QuestSetCompleted(..., false)` 当成任务完成。
- 已确认语义的 CustomVictoryBJ、CustomDefeatBJ 和原生玩家结算调用。普通结束／离开游戏、剧情坏结局、函数名含 Defeat 或单纯提示文字，不能仅凭名字归类成真正判负。
- 事件注册、条件函数与动作的联系；死亡、进入区域、计时、周期事件、主动调用触发器等。TriggerExecute、ConditionalTriggerExecute、TriggerEvaluate、ExecuteFunc 等不能混同；无法解析的动态函数名保留未知。
- 初始化、禁用／启用触发器、计时启动、调用路径上的附加条件。不能把“脚本中存在调用”说成“本次游戏一定执行”。

从任务完成／失败设置和关卡结算调用反向追踪：调用者 → 分支条件 → 触发事件／初始化入口。条件按路径保留 AND/OR、否定、顺序及难度分支；不把不同触发路径合成一个 AND 条件。

计数与变量：显示实际比较符号和阈值，追踪可解析的初始化、加减、赋值及任务条目来源。不能确定来源或运行时值时保留原表达式，并说明未解析；不显示猜测的当前进度。例如 `x >= 4` 与 `x == 4` 必须分别展示。

库和包装：已知 BJ／常量语义需来自匹配构建的标准库或经过验证的规则；先检查地图是否重定义／遮蔽同名函数，不能对任意同名包装套用标准语义。未知包装继续追踪其可取得的函数体，缺失或动态行为标记缺口。

任务对象无法确定、指针／数组别名冲突、没有任务对象的直接胜败判定，放入“未关联到具体任务的条件”，不擅自归到某个任务。自建 UI 任务系统没有标准 quest 调用时，明确说明只识别到结算或其他脚本线索，不能宣布完整枚举。

## 结果模型和可解释性

每次报告绑定不可变来源快照。基本数据包括：

- 来源：连接／会话身份、章节资源路径、脚本语言与哈希、字符串表来源、检测时间。
- 任务：脚本标识、能确认的名称／说明、主线／支线等脚本属性、任务条目、创建路径、完成和失败判定。
- 条件证据：类别、目标玩家／任务、事件、结构化条件表达式、调用路径、辅助变量来源、原函数与行号、支持该结论的源片段。
- 覆盖情况：已解析的任务定义数、条目数、结算点、未解析调用／分支／字符串和具体原因。

名称解析优先使用同来源字符串表，保留作者原文；TRIGSTR 或动态拼接不明则保留编号／表达式，不猜标题。不能把静态初值当成本次运行状态，也不把被禁用、尚未证明可达的定义静默删除。

覆盖状态至少区分：未连接、未进入地图、来源无法确认、正在检索、不支持脚本、部分解析、分析完成、会话已变化、取消／超时／失败。只有所支持分析域内没有未解析目标或调用缺口时才可用“分析完成”；文案始终说明这是脚本静态分析。成功取得脚本不等于条件完整。

## 界面、刷新和线程

建议新增“任务与条件”页，不改变现有 ID 页和大象功能布局。进入地图、连接成功并打开此页后自动进行首次检索，另提供“重新检索”按钮。只在本页需要显示信息时检测，不在所有页面不断全量分析；这是实现者提出的触发方式。

先显示检索状态，来源确认和分析结束后再发布结果。左侧按任务／关卡胜败列出结果，右侧显示完成条件、失败条件及证据；提供按名称、变量或条件文字搜索。未解析条目必须在列表和详情可见，不能只藏在日志。

条件中文解释仅翻译经过识别的语法／函数；任务名、角色名和变量原文保留。新增普通界面文案纳入现有中英文切换。用户可以选择详情文本，不增加执行任务、完成任务、修改触发器或额外快捷键。

后台执行来源读取与解析，工作线程不访问 Tk。检测、取消、连接变化及地图切换分别更新 generation；旧任务不能覆盖新结果。沿用 R21 的实际校验时间，队列延迟不能使过期结果重新有效。地图变化立即清理旧报告；重新进入任务页先校验来源再显示或重新检索。隐藏页不持续全量查询。

## 资源上限和异常

设置脚本／字符串字节数、词法和语法节点数、函数数、调用深度、路径数、任务数、总耗时等上限，避免递归调用、循环或路径爆炸卡死界面。具体阈值由实现者用样本确定并写成可测常量。任何超限必须显示原因和覆盖不足，不截断后声称“全部条件”。取消后释放临时文件、缓冲区和任务状态。

复用已验证的只读档案接口、字段校验、目标构建限制和串行 helper 通道。对不可信脚本只解析数据，不 eval、exec、加载为模块或调用地图函数；不跟随任意外部文件、网络地址或脚本提供的命令。游戏资源路径作为数据校验，不作为 shell 参数拼接执行。

## 验收与交付

1. **来源证据先行：** 正确绑定当前地图，至少两张不同脚本的地图／章节；菜单、换图、断线、进程重启、源档案变动及旧任务回包均不发布旧报告。若来源未证明可靠，不宣称功能完成。
2. **解析器测试：** 字符串／注释伪调用不误报，布尔优先级、早返回、多调用路径、事件注册、禁用／启用、计数初值和增量、难度分支、数组／别名、未知包装、递归、动态调用、无任务的直接结算、重置 false、截断／超限／取消。每条重要逻辑先失败再修复。
3. **人工脚本对照：** 《亡灵骑士》第三章必须能解释上述计数、区域和两处直接失败，并追踪直接胜利的调用者。再核对至少一章具有不同任务结构的样本。每项都能从界面定位到真实函数／行号；数量不能用同一解析器的输出自证完整。
4. **覆盖与界面：** 不支持 Lua 或无法确认脚本不能显示空表成功；任务与关卡结算不误关联；中文解释和原表达式并列；未知条件、来源、快照时间可见；连接和旧队伍／ID 监视不被破坏。
5. **回归与包：** 运行相关测试及完整回归，独立最终审阅后处理重要问题；若新增 helper 协议则验证与 EXE 配套。冻结 EXE 自检、源码／DLL 一致性、源码 ZIP CRC／Git blob 与副本哈希检查齐备。
6. **交付：** 独立 R22 测试 EXE、匹配源码、中文使用及验证记录、校验文件；保留 R21 与旧版本。本次不自动上传 GitHub。

实现期间若需游戏内定位或切换章节，先请求用户自行打开地图并保存进度；不擅自启动、关闭或切换游戏，不改变当前游戏状态来制造条件。只读静态结论、运行时来源证明与实际游戏条件触发测试分别记录，不能互相冒充。
