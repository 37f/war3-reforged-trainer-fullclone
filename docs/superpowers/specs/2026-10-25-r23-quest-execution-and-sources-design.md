## 5. 完成入口的识别与资格

新增独立的完成计划模型，不把 R22 的 `QuestReport` 成功解析等同于允许执行。每个计划绑定：来源快照、任务定义键、实际运行中任务身份、完成入口、可解释调用链、完整性／拒绝原因、状态与副作用证据。

### 5.1 最小可用支持范围

- 找到属于该任务的明确完成设置与原完成动作链；任务名称相同仍按各自脚本对象区分。
- 入口必须是本次已加载地图中的已确认无参数、无返回值完成动作／函数，不接受用户自由输入函数名或任意地址。
- 需要证明调用的是完整的原完成流程：保留它自己的奖励、解锁、触发器启停与后续调用；不能只调用深层 setter 辅助函数而漏掉调用者中的奖励。
- 原函数内部的条件保持原样。若它仍依赖未达成的计数／物品／区域等条件，不能宣称强制完成可用；首版拒绝该入口，不任意改变量或跳转到函数中段。
- 依赖死亡／进入区域等事件响应值、触发器身份、枚举上下文、动态函数名、未知调用、无法绑定的任务别名或不确定触发器实例时，标注缺失上下文并禁用，除非能在精确构建上证明可通过原实例完整建立该上下文。
- 不执行初始化／创建任务函数以制造缺失任务，不把尚未创建的静态定义当成可执行任务。
- 入口包含多个任务或多种无法确定的完成分支，不能任选一条。需要执行的奖励若位于无法唯一关联的另一条事件链，也标记暂不支持完整完成。

这是一组资格要求，不是宣称已证明的实现能力。实际支持的语法和函数集合由测试与运行时调查收敛，拒绝原因必须具体显示。

### 5.2 副作用展示

预览显示已识别的奖励、单位／物品变化、解锁、后续触发器、剧情以及关卡结算调用；无法静态确认的部分注明未知。原完成流程确实调用关卡胜利或切章时如实提示，该流程可以作为用户所选任务的后续执行；不增加“全任务完成”或任意胜败按钮。

状态读回只能证明对应状态。调用原动作和看到任务已完成，并不自动证明所有奖励和远期剧情都已验证；验证记录分别列出状态、奖励、解锁和剧情证据。

## 6. 持久 helper 执行桥与运行时核对

先调查，再确定新查询／执行操作的细节和未占用编号；若协议或 DLL 更改，升级配套版本并保留旧操作的全部含义，不改旧 native 名称、签名、hash、读取接口或 121 等历史操作。

调查需分别证明：

1. 能在当前活跃 JASS VM 内把脚本中已确认的 quest／trigger 全局标识解析为当前有效对象，验证类型、实例和状态；首版可只支持标量或明确常量下标，其余拒绝。
2. 能验证目标函数在当前 VM 存在，签名符合计划，且属于同一脚本版本。
3. 能通过已验证的 JASS 调用机制（优先研究 ExecuteFunc）在正确游戏线程／脚本上下文执行。不能把原生 handler 需要的 JASS 字符串直接换成 `char*`，也不能把 JASS 函数当普通 C 函数地址调用。
4. 遇到睡眠、异步剧情或其他触发器时，正确记录已派发状态并读回；不能因一次原生调用返回就显示全部完成。

这部分是新的可行性门槛。若无法证明，则提交可核对的调查结果，不能交付一个实际只设置标志的“完成任务”按钮。

### 6.1 用户执行顺序

1. 自动检索后，用户在现有任务页选中任务。
2. 点击“检查完成入口”，后台进行只读资格与实时状态核对，并展示原流程、来源和拒绝原因。
3. 条件满足时开放“完成此任务（原流程）”按钮，点击才进行一次执行。
4. 执行前在 helper 串行通道重新核对同一进程、连接代际、地图会话、脚本／存储版本、VM、任务身份和入口；已完成、已失败、已销毁、未创建或来源变化都拒绝。
5. 执行与去重绑定同一个计划身份，并在游戏线程处理时再次核对，不能只依赖 Tk 检查。
6. 返回可区分的结果：拒绝且未派发、已派发待观察、任务状态已读回完成、结果未知／已换图。失败后不自动重试，不根据 RPC 超时判断一定没有执行。

预览通过不自动执行；任务页定时刷新、自动检索、换语言和选择条目均不能触发动作。每次用户明确点击才执行。首版不设置新快捷键，也不要求每次重复确认同一弹窗。

### 6.2 重复、取消与恢复边界

同一会话／同一实际任务实例的已派发请求保持去重记录，UI 双击、排队、超时或自动刷新不重复发奖。计划在重新检索后不能绕过去重。读取到未完成也不能擅自认定前次动作没有启动。

去重记录应由游戏侧持久 helper 在同一地图会话内保存，修改器重连或关闭页面不清除。若 helper 被替换或状态丢失，无法确认前次请求是否已派发时拒绝再次执行，不以重建 Python 控制器清除不确定性。具体记录容量与清理策略留给实施者确定并测试。

取消只影响尚未派发的请求和后续查询；动作一旦派发，就不能承诺撤销剧情或奖励。不得提供通过恢复一个 quest 标志来伪装“恢复任务”。用户实测前保留恢复存档；不自动覆盖／编辑存档，不代替用户切换章节。

用户打开游戏和选择具体测试任务后再进入实测，不擅自启动／关闭／切图；先核对来源和任务，再执行用户选择的任务。使用恢复存档，记录原流程奖励和解锁的实际结果。
